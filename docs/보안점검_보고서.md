## 고친 문제

### OWASP-A06-001 · 무거운 SQL이 DB와 처리 자리를 오래 붙잡을 수 있음
- **분류:** A06 Insecure Design. 소비 자원 제한 누락으로, 이 가이드의 A06 매핑 목록에서는 CWE-799(상호작용 빈도 제어 부족)에 가장 가깝습니다. 자원 고갈(CWE-400)은 가이드의 매핑 목록에서 확인하지 못해 그대로 적습니다.
- **심각도:** 중간 — 서비스 거부(응답 지연) 가능. **확신도:** 높음(경로와 실제 동작 확인).
- **위치:** `backend/app/chaesan/local/db.py` (`SqliteDB._run`)
- **진입점과 경로:** 사용자 질문 → LLM이 SQL 작성 → `validate_sql` 검사 → `SqliteDB.query`. 검사기는 SELECT·허용된 표·행 수 상한만 확인하고, **같은 큰 표(21만 행)끼리의 조인은 통과시킵니다.** 실제로 `FROM t_15138735 a JOIN t_15138735 b ON 1=1`을 검사기가 허용하는 것을 확인했습니다.
- **영향:** 실행 시간 제한이 없어 한 질문의 조회가 오래 돌고, 동시 처리 자리 2개를 붙잡으면 다른 사용자는 모두 503을 받습니다.
- **조치:** SQLite의 진행 확인 함수(`set_progress_handler`)로 **조회 1건당 2초 제한**을 걸었습니다. 시간이 지나면 SQLite가 조회를 중단하고(`interrupted`) 엔진은 이를 "조회 실패"로 처리합니다.
- **확인:** 실제 21만 행 표에서 정상 집계는 0.00초, 자기 조인은 정확히 2.00초에 중단됩니다. 회귀 테스트 3개(`test_chaesan_security.py`).
- **참고:** OWASP Cheat Sheet — Denial of Service, Query Parameterization.

### OWASP-A06-002 · 요청 제한의 사용자 구분 값 우회
- **분류:** A06, CWE-799. **심각도:** 중간(IPv6 사용자 또는 프록시 뒤 배포에서). **확신도:** 중간(배포 구성에 따라 달라짐).
- **위치:** `backend/app/chaesan/local/ratelimit.py` (`client_ip`)
- **경로:** 연결 상대가 같은 컴퓨터(터널·프록시)일 때 `CF-Connecting-IP` 헤더 값을 **검증 없이** 사용자 구분 키로 썼습니다. (1) IPv6 사용자는 보통 /64 전체(2^64개) 주소를 받아서, 주소를 바꿔 가며 분당·하루 제한을 피할 수 있었고, (2) 프록시가 헤더를 덮어쓰지 않는 배포에서는 요청마다 다른 값을 보내 제한을 피하고 메모리 키를 늘릴 수 있었습니다.
- **조치:** IP 모양이 아니면 헤더를 버리고, IPv6는 **/64 묶음 하나**로 셉니다.
- **확인:** 같은 /64의 주소 199개와 엉터리 헤더 50개가 각각 한 키로 모이는지 시험(`test_rotating_ipv6_addresses_or_garbage_headers_cannot_evade_the_limit_key`).
- **남은 위험:** 프록시(Caddy 등)가 외부에서 온 `Cf-Connecting-Ip` 헤더를 그대로 전달하면 여전히 위조할 수 있습니다. **배포 때 프록시가 이 헤더를 직접 덮어쓰도록 설정해야 합니다**(아래 "남은 위험" 1번).

### OWASP-A02-001 · 화면 폴더 전체가 웹으로 공개됨
- **분류:** A02 Security Misconfiguration. 가이드의 A02 매핑 목록에 정확히 맞는 CWE가 없어 CWE는 붙이지 않았습니다.
- **심각도:** 낮음(공개 저장소라 내용은 이미 공개이지만 불필요한 노출). **확신도:** 높음.
- **위치:** `backend/app/chaesan/local/app.py` (`StaticFiles`)
- **경로:** 화면 폴더(`frontend/`) 전체를 서빙해서 `tests/`, `package.json`, `README.md`, 점 파일(`.gitignore`)까지 URL로 내려갔습니다.
- **조치:** **허용 목록**(`index.html`, `privacy.html`, `favicon.svg`, `css`, `js`, `img`, `data`)만 서빙합니다. 목록이 실제 화면 파일과 어긋나면 테스트가 실패합니다.

### OWASP-A10-001 · 사용 기록 실패가 정상 응답을 500으로 바꿀 수 있음
- **분류:** A10, CWE-755(예외 조건의 부적절한 처리). **심각도:** 낮음. **확신도:** 높음.
- **위치:** `app.py`의 사용 기록 미들웨어. 기록기는 `OSError`만 삼켰고, 다른 예외가 나면 응답이 500으로 바뀔 수 있었습니다.
- **조치:** 기록 중 어떤 예외가 나도 응답은 그대로 보내고 경고만 남깁니다. 시험용 "폭발하는 기록기"로 확인했습니다.

### OWASP-A10-002 · 요청을 받는 도중 연결이 끊기면 서버 오류(500)
- **분류:** A10, CWE-755. **심각도:** 낮음. **확신도:** 높음(코드 경로).
- **조치:** `ClientDisconnect`를 400으로 처리합니다. 5MB 조각 요청, 큰 `Content-Length`, JSON이 아닌 형식(415) 공격은 실제 서버에서 확인했습니다.

### OWASP-A09-001 · 차단 기록의 질문 지문이 키 없는 해시였음
- **분류:** A09, CWE-532(민감 정보가 로그에 남음)에 가까움. **심각도:** 정보(낮음). **확신도:** 높음.
- **위치:** `backend/app/chaesan/core/guard.py` (`_fingerprint`)
- **경로:** 지시문 공격이 차단될 때 질문의 SHA-256 앞 8자를 로그에 남겼습니다. 짧은 문장은 후보를 대입해 원문을 짐작할 수 있습니다.
- **조치:** 프로세스마다 새로 만드는 키의 HMAC으로 바꿨습니다(같은 프로세스 안에서만 같은 값 → 반복 횟수는 세고 원문은 못 알아냄).

## 점검 중 바로 고친 작은 것
- `backend/.env` 파일 권한이 `644`(다른 계정이 읽을 수 있음)였던 것을 `600`으로 바꿨습니다(Cloudflare 토큰이 들어 있는 파일). 개인 노트북이라 위험은 낮았지만 서버로 옮길 때도 같은 권한을 유지해야 합니다.

## 남은 위험 (배포 때 처리)
1. **프록시 헤더 위조(A02/A06):** 오라클 서버에서 Caddy를 쓸 때 `Cf-Connecting-Ip`를 프록시가 `{remote_host}`로 덮어써야 합니다. 임시 터널(cloudflared)에서는 Cloudflare 엣지가 이 헤더를 붙여 위조되지 않습니다. 배포 설정이 생기면 다시 점검합니다.
2. **GitHub Actions 참조 고정(A03/A08, 정보):** `.github/workflows/deploy-pages.yml`이 `actions/checkout@v4`처럼 **태그**로 참조합니다. 커밋 해시로 고정하면 더 안전합니다. 이 워크플로는 수동 실행 전용이라 위험이 낮습니다.
3. **알림 체계 없음(A09):** 차단·한도 초과가 기록은 되지만 사람에게 알려 주는 장치가 없습니다. 이번 규모(하루 약 340건 한도)에서는 일별 요약 도구로 확인하는 것으로 충분하다고 판단했습니다.

## 점검하지 못한 것 (한계)
- **배포 환경:** HTTPS 종료 지점, 프록시 설정, 서버 계정 권한은 아직 없습니다.
- **실제 Cloudflare AI를 붙인 상태의 지시문 공격 재시험:** 개발용 20문항 정확도는 재었지만, 공격 문장 모음을 새 모델에 다시 돌려 보지는 않았습니다(기존 시험은 가짜 LLM과 로컬 모델 기준).
- **Cloudflare 쪽 데이터 처리:** 모델 페이지에 "데이터 비보관"으로 표시돼 있는 것을 확인했을 뿐, 실제 처리는 확인하지 못했습니다.
- **정적 점검의 본질적 한계:** 업무 의도, 클라우드 계정 설정, 런타임 버전별 동작은 코드만으로 확인할 수 없습니다.
